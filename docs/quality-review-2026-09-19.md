# ARU STAY 품질 검증 · 2026-09-19

> 이 문서는 수정 전 검증 기록이다. 후속 조치와 현재 상태는 [리뷰 후 수정 결과](review-fixes-2026-09-19.md)를 참고한다.

## 결론

**라우팅·다국어·기본 검색 정보는 검증한 범위에서 안정적이다. 그러나 시각적 마감과 성능 검증까지 끝난 상태는 아니다.**

현재 화면은 실제 간판 사진, 원본 로고, 갈색·크림 팔레트로 브랜드의 출발점을 갖췄다. 반면 본문의 반복적인 구성, 준비 중 콘텐츠의 비중, 서로 다른 시작 기준을 가진 랜딩 모션 때문에 완성도가 고르지 않다. “AI 티가 전혀 없다”거나 임의의 점수로 “90점 이상”이라고 판단할 근거는 없다.

이번 작업은 리뷰다. 애플리케이션 코드를 수정하거나 커밋·푸시·배포하지 않았다. 더미 콘텐츠는 사용자가 허용한 범위이며 구현 실패와 구분했다.

## 1. 검사 대상과 증거 수준

- 현재 작업 폴더에서 새로 프로덕션 빌드한 Next.js 16.2.3 사이트를 `http://localhost:3101`로 실행했다.
- 검사 시작 시 이전 작업본과 현재 작업 폴더의 소스 140개가 바이트 단위로 일치했다. Git 기준점은 `977317069097aee3d7665115b233a751d5fafb43`이며, 리뉴얼 변경은 미커밋 상태다.
- 관리자 CMS, 실제 운영 환경 변수, 결제·외부 예약 시스템은 이번 공개 화면 검사의 범위에 포함하지 않았다.
- 실제 관찰, 코드에서 도출한 계산, 디자인 의견을 구분한다. 계산상의 대비 수치는 스크린샷 픽셀 추정값이 아니라 브라우저의 CSS 색상과 불투명도에서 구했다.
- 이 보고서는 현재 구현 자체의 리뷰다. 원래 프로토타입과의 최신 화면별 재대조나 실제 사용자 선호도 실험은 수행하지 않았다.

상태 정의: `verified`는 명시한 조건에서 실행 검증됨, `implemented-not-executed`는 구현만 확인됨, `partially-verified`는 필요한 일부만 확인됨, `not-satisfied`는 명시한 기준의 위반이 확인됨, `not-verifiable`는 현재 증거로 판단할 수 없음을 뜻한다.

## 2. 우선 확인·수정할 항목

### A. 소개 사진이 내장 브라우저에서 표시되지 않음

**우선순위: 마감 전 확인 / 관찰된 표시 기준: `not-satisfied` / 원인과 다른 브라우저 재현 여부: `not-verifiable`**

- 영어 홈, 내장 브라우저 1440×900에서 About 앵커로 이동했을 때 운영자 사진 대신 아치 형태의 단색 배경이 남았다.
- 같은 위치에서 새로고침한 뒤에도 `complete: false`, `naturalWidth: 0`, `currentSrc: ""`였다. 사진 영역 자체는 420×451.5px로 존재했다.
- 부모 reveal 상태는 `in`, 불투명도는 1이어서 단순히 페이드가 끝나지 않은 상태와는 구분된다.
- `/images/optimized/about.avif`는 HTTP 200, 351,012바이트였다. `/_next/image?...about.avif&w=640&q=75`도 HTTP 200, 25,016바이트로 응답했다.
- 파일 누락은 확인되지 않았다. 내장 브라우저의 지연 로딩·뷰포트 처리인지 일반 브라우저에서도 발생하는 구현 문제인지는 아직 확정할 수 없다.
- 관련 코드: `app/[locale]/sections/About.tsx:16`. 사진 로딩, 앵커 진입, 새로고침을 일반 Chrome/Safari와 실제 모바일에서 확인한 뒤 조치해야 한다.

### B. 첫 화면 설명문이 애니메이션 초기에 흐려짐

**우선순위: 마감 전 수정 / 애니메이션 전 구간 4.5:1 유지 기준: `not-satisfied`**

모바일 첫 화면은 단색 배경 `#4f372f`다. 설명문 `#eadfcc`는 16px이며, `.hero-copy` 전체가 opacity 0.55에서 1로 변한다.

| 대상 | 시작 대비 | 종료 대비 | 4.5:1 미만으로 계산되는 시간 |
| --- | ---: | ---: | ---: |
| 설명문 | 3.710:1 | 8.295:1 | 약 0.478초 |
| 위치 비교 링크 | 4.038:1 | 9.314:1 | 약 0.334초 |

정지 상태의 색 조합은 충분하다. 문제는 읽는 본문까지 한꺼번에 흐리게 만드는 등장 효과다. 큰 제목에는 다른 대비 기준이 적용되므로 위 수치를 제목에 그대로 적용하지 않았다. 사진 위에 놓이는 데스크톱 본문도 같은 수치라고 주장하지 않는다.

일반 텍스트의 최소 대비 기준은 4.5:1이다. 이는 전체 사이트에 대한 접근성 인증 결과가 아닌, 해당 모바일 상태에 대한 국소 검사다. [W3C 대비 기준](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html)

관련 코드: `app/globals.css:414`, `app/globals.css:425`. 본문과 조작 링크의 불투명도를 유지하는 쪽을 권한다. 현재 색상에서 설명문이 4.5:1을 넘는 계산상 최소 opacity는 약 0.647이지만, 임계값에 맞추는 것보다 처음부터 읽을 수 있게 두는 편이 낫다.

### C. 랜딩 사진과 문구의 시작 시계가 다름

**우선순위: 모션 재설계 / 구조 확인: `verified` / 느린 네트워크 체감: `not-verifiable`**

- 문구: CSS 애니메이션 시작 후 1.6초.
- 사진: 이미지 `onLoad` 이후 2.2초.
- 두 요소를 묶는 공통 시작 상태나 시간표가 없다.

따라서 문구 시작을 0, 사진 준비 지연을 `d`라고 놓으면 종료 시점은 각각 `1.6초`, `d + 2.2초`다. 이는 코드에서 확인되는 관계이며, 실제 느린 네트워크의 `d` 값을 측정한 결과는 아니다.

시간만 늘려도 두 동작이 하나의 장면으로 맞춰지는 것은 아니다. 사진 로딩이 늦으면 문구가 정착한 뒤 사진이 따로 움직이는 상황이 가능하다. 같은 타임라인으로 조율하거나, 읽는 문구를 고정하고 사진에만 절제된 동작을 남기는 방향이 적합하다.

관련 코드: `components/renewal/HeroImage.tsx:14`, `app/globals.css:422`, `app/globals.css:425`.

### D. 린트 명령이 실행되지 않음

**우선순위: 다음 코드 마감 전에 수정 / 상태: `not-satisfied`**

`npm run lint` 실행 결과는 exit 1이다.

```text

```

`package.json:9`는 `next lint`를 실행하지만 Next.js 16은 이 명령을 제거했다. 현재 빌드 성공은 ESLint 검사 성공을 뜻하지 않는다. [Next.js 16 안내](https://nextjs.org/docs/app/guides/upgrading/version-16#eslint)

기준 커밋에도 같은 명령이 있어 이번 리뉴얼에서 새로 생긴 문제는 아니다. 현재 저장소의 품질 검사를 정상화하려면 ESLint CLI와 설정을 정리해야 한다.

### E. 공개 페이지에 사용하지 않는 Inter를 미리 불러옴

**우선순위: 성능 정리 / 불필요한 preload 확인: `verified`**

| 미리 불러오는 글꼴 | 파일 크기 |
| --- | ---: |
| ARU Display Latin Medium | 23,324 B |
| ARU Display Latin Bold | 23,664 B |
| Inter Latin | 48,432 B |
| 합계 | 95,420 B |

공개 홈의 실제 본문은 시스템 서체, 제목은 ARU Display다. 보이는 제목·문단·버튼·링크의 계산된 font-family에 Inter는 없었다. 그런데 HTML과 Next 폰트 manifest에는 Inter preload가 포함되어 있다.

`app/admin/layout.tsx:5`에서 Inter를 선언한다. 공개 경로로 preload가 들어오는 정확한 빌드 경로까지 확정한 것은 아니며, 관리자 글꼴의 preload 범위와 공통 CSS 포함 방식을 점검해야 한다.

48,432 B는 해당 압축 글꼴 파일 크기다. 재방문 캐시와 요청 우선순위에 따라 영향이 달라지므로 LCP가 몇 초 나빠진다고 환산하지 않는다.

### F. 갤러리 터치 방향 판별이 불완전함

**우선순위: 모바일 실기 검증 / 코드상 반례 확인 / 기기 재현: `not-verifiable`**

`components/renewal/RoomGallery.tsx:74`는 `abs(Δx) > 45`만 판단하고 세로 이동량을 비교하지 않는다. `Δx=60px`, `Δy=300px`는 수직선에서 약 11.3° 벗어난 세로 스크롤인데도, touchend가 전달되면 사진 전환 조건을 만족한다.

실제 기기에서는 touchcancel 등 브라우저 동작에 따라 결과가 달라질 수 있다. 현재 데스크톱 브라우저 검사로 “휴대폰에서 오작동했다”고 결론 내리지는 않는다. 수평 이동이 세로 이동보다 우세한지까지 판별하는 것이 적절하다.

## 3. 모션의 수학적 검토

현재 easing은 `cubic-bezier(0.33, 0, 0.67, 1)`이다. 정규화한 시간 `x`, 진행률 `y`는 매개변수 `u ∈ [0,1]`에 대해 다음과 같다.

```text
x(u) = 0.99u + 0.03u² − 0.02u³
y(u) = 3u² − 2u³
화면 이동량 = 22 × (1 − y) px
불투명도 = 0.55 + 0.45y
```

| 항목 | 계산값 | 해석 |
| --- | ---: | --- |
| 문구 전체 시간 | 1.600초 | 설정값 자체는 짧다고 단정하기 어려움 |
| 이동의 10→90% 구간 | 0.977초 | 이동 대부분이 약 1초에 집중됨 |
| 문구 평균 이동 속도 | 13.75px/s | 전체 22px 이동 |
| 문구 최고 이동 속도 | 20.52px/s | 중간에서 가장 빠름 |
| 0.8초의 남은 이동량 | 11px | 절반 시점에 절반 이동 |
| 사진 전체 시간 | 2.200초 | 이미지 준비 시점부터 시작 |
| 사진 변화의 10→90% 구간 | 1.343초 | 사진은 문구보다 늦게 마무리됨 |
| 사진 배율 | 1.045 → 1.000 | 변화량 4.5% |
| 일반 사진 진입 페이드 | 1.300초 | 스크롤 진입 시 한 번 실행 |

1440px 너비 요소를 중심 확대한다고 가정하면 좌우 가장자리 이동은 각각 `1440/2 × 0.045 = 32.4px`, 390px에서는 `8.78px`다. 이는 요소 경계의 기하학적 비교이며, object-cover로 잘리는 실제 피사체의 이동량을 그대로 뜻하지 않는다.

스크롤 효과는 실제 사진 4개에만 적용된다. 위치 이동은 0px이며 opacity 0.45→1이다. 사용자가 스크롤한 거리에 따라 되감기거나 진행하는 효과가 아니라, 진입을 계기로 시간에 따라 끝나는 효과다. 그러므로 “페이지 전체가 스크롤에 반응한다”는 인상을 기대하면 지금 구현은 약하게 느껴질 수 있다.

**판단:** 어색함의 주된 후보는 절대 시간 부족보다 시작 기준의 분리, 모바일에서 작아지는 사진 움직임, 본문까지 함께 흐려지는 처리다. 이는 코드·계산에 기반한 디자인 해석이며 사용자 실험으로 인과관계를 증명한 것은 아니다.

### 페이지 길이

- 영어 홈 390px 폭: 9,001px.
- 844px 높이로 나누면 약 10.66개 화면 분량이다. 실제 스와이프 횟수나 유효 가시 영역을 뜻하지 않는다.
- 영어 홈 1440px 폭: 6,072px, 900px 높이 기준 약 6.75개 화면 분량.
- 길이 자체는 오류가 아니다. 그러나 사진·사양이 확정된 객실이 2개뿐인 현재 정보량과 비교하면 모바일에서 긴 편이라는 판단이다.

“AI 티”는 검증 가능한 단일 수치가 아니다. 현재의 일반적인 인상은 주로 반복된 제목·설명 패턴, 추상적 문구와 임시 콘텐츠에서 나온다는 것이 이번 시각적 평가다. 애니메이션이나 아이콘을 늘린다고 해결된다고 보지 않는다.

## 6. SEO·다국어·GEO 판단

### 확인된 기본 처리

- 48개 페이지의 제목·설명·언어·canonical·4언어 hreflang·x-default 경로가 검사 기준과 일치한다.
- 더블룸·트윈룸의 검색 설명이 서로 다르다.
- Open Graph 언어, 대체 언어, 공유 이미지 설명, Twitter 제목을 확인했다. 공유 이미지 5개가 정상 응답했다.
- 사이트맵은 색인 허용 대상으로 설정된 16개 URL이다. 초안 32개 페이지는 noindex이고 사이트맵에서 제외된다. 이 숫자는 실제 색인 완료 수가 아니다.
- 예시 후기에는 `data-nosnippet`이 있고, 허위 평점 구조화 데이터는 추가하지 않았다.
- 공통 Organization과 확인된 왕십리 지점의 LodgingBusiness 데이터가 있다. 동대문에 왕십리 주소를 복제하지 않는다.

### 확인되지 않은 성과

- 운영 도메인의 실제 색인·검색 순위·Search Console 상태.
- Google/ChatGPT/Claude/Grok이 실제로 수집·인용하는지와 언어별 노출 성과.
- 원어민 수준의 전 문장 교정 및 운영자가 확인한 사실 정확성.
- 운영 환경의 canonical 도메인과 환경 변수 설정.

따라서 **“다국어 정보를 읽을 수 있는 기본 구조가 있다”는 평가는 가능하지만, “외국어 AI 검색 대응을 완료했다”는 결론은 불가능하다.**

## 7. 성능 판단

메인 사진 파일은 JPEG 586,775 B에서 AVIF 194,350 B로 66.88% 작아졌다. 제목 글꼴은 라틴 문자 두 개 합계 46,988 B를 미리 불러온다. 다만 별도로 확인된 Inter 48,432 B가 있어 공개 홈의 글꼴 preload 합계는 95,420 B다.

이것은 저장 파일·응답 크기의 개선이다. 페이지 전체 전송량, 느린 네트워크의 첫 화면 속도, 실제 사용자 반응 속도를 뜻하지 않는다. Next 이미지 최적화 응답과 브라우저 캐시에 따라서도 실제 전송량이 달라진다.

LCP·INP·CLS의 운영 실측값은 확보하지 못했다. 좋은 사용자 경험의 기준은 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하이며 실제 사용자 75백분위수 기준으로 판단한다. 이번 결과로 그 기준을 통과했다고 말하지 않는다. [Google Core Web Vitals 안내](https://developers.google.com/search/docs/appearance/core-web-vitals)

## 8. 합의된 임시 콘텐츠와 배포 조건

- 예약 URL: 0/2. 현재는 준비 중 안내와 이메일 문의까지 동작한다. 실제 예약 완료는 `not-verifiable`이며 URL 연결 후 외부 흐름 검증이 필요하다.
- 객실 사진: 2/6. 초안 객실 4개와 동대문 정보는 합의된 준비 중 콘텐츠다.
- 정책·후기·소개 문구 일부는 초안이다. 이를 새 구현 결함으로 계산하지 않았다.
- 현재 상태의 검토용 공개와 실제 예약을 받는 운영 공개는 필요한 조건이 다르다. 운영 예약 사이트라고 판단하려면 실제 예약 연결이 필요하다.
- Vercel의 현재 Git 자동 배포 연결과 운영 브랜치는 이번 턴에서 재확인하지 않았다. “푸시하면 자동으로 정확한 곳에 배포된다”고 이번 리뷰만으로 보장하지 않는다.
- 배포 작업 전에 Vercel CLI 58.5.1을 최신 버전으로 올리는 것을 권한다. 세션에서 안내된 최신 버전은 59.23.2다. 명령: `npm i -g vercel@latest`. 이번 리뷰에서는 설치하지 않았다.
